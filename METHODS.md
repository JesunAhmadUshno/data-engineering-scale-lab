# Methods

## Design

One research question (RQ1, PREREG.md), three arms, identical input files,
identical SQL logic, one machine. The arms differ only in the engine or
framework under test:

- Arm A: DuckDB 2.0.0 over Parquet, canonical SQL run as written.
- Arm B: Apache Spark 4.0.1, local[*] (four worker threads on this
  machine), same Parquet files read as temporary views, canonical SQL run
  as written.
- Arm C: dbt Core 1.12.6 with dbt-duckdb 1.11.1 on the same DuckDB engine;
  staging views over the same Parquet files, intermediate and mart models
  whose SQL is the canonical SQL with ref() wrappers. A parity script
  (src/check_sql_parity.py) normalizes the models back to canonical form
  and diffs them; it passes for all six transformations.

The canonical SQL lives in sql/. The dbt incremental models (T3, T4)
carry one registered addition: an is_incremental() filter that restricts
recomputation to the order dates named by the delta. That filter is the
mechanism under test in H4 and H6, not a logic difference; the parity
script removes exactly that block before diffing.

## Data

Generated locally by DuckDB's tpch extension (call dbgen), exported once
to Parquet, read identically by all arms. Derived from TPC-H; see
LICENSES.md. Scale ladder SF0.1, SF1, SF10 (lineitem about 0.6M, 6M, 60M
rows). SF10 is generated in ten split chunks with the dbgen children and
step parameters, one Parquet part file per chunk; the arms read the part
files as one table through a glob, so the input is still one identical
file set. SF30 was cut before preregistration as a machine limit
(PREREG.md Section 4).

The late delta is synthetic, generated by fixed arithmetic with no random
generator (data/gen/synth.py): 40 new orders and 120 new lineitems on
three existing order dates, plus one existing lineitem whose price is
multiplied by 1.5. Any reviewer regenerates the identical delta from the
identical base data.

## Timing protocol

- Five measured runs per cell (arm x scale x transformation), preceded by
  one uncounted warm-up pass per arm per scale (PREREG.md Deviation 1).
- Reported per cell: mean, sample standard deviation, coefficient of
  variation. Cells above 30 percent CV are named in RESULTS.md with the
  cause when known; sub-100 ms DuckDB cells carry timer jitter of the
  same order as the measurement, and their CVs say so.
- Arm A and Arm B times are execution plus output write, measured around
  the write call. Arm C times are dbt's own per-model execution_time from
  target/run_results.json; the full dbt build wall time is logged beside
  them and is always larger, because it includes staging, tests in build,
  and dbt's own startup. The two timing bases are not mixed in one ratio:
  H1 and H2 use Arms A and B only. Arm C is reported for cost context and
  for the gate and incremental results.
- Setup overhead is measured and reported separately (PREREG U-11):
  Arm A, connect plus input views; Arm B, JVM start, session creation,
  and a first trivial action; Arm C, the build wall time includes dbt
  startup by construction and is labelled as such.
- Engine settings, held constant across scales and recorded in the run
  log: DuckDB memory limit 2.2 GB, 4 threads, spill to local disk; Spark
  driver memory 1600 MB, shuffle partitions 8 (16 at SF10), adaptive
  query execution on, task results returned directly (see DECISIONS.md
  D3 for why that setting exists on this machine). One exception: the
  dbt arm at SF10 runs with one thread and a 1.8 GB memory cap instead
  of two threads and 2.2 GB, after two builds were killed during the
  largest join model under memory contention (DECISIONS.md D14). dbt
  times are never compared across scales, and the SF10 incremental
  comparison (H6) uses the same settings on both sides.

## Correctness protocol

SHA256 over the ordered output (ORDER BY all output columns), exported
through one fixed writer (DuckDB COPY to CSV with fixed options) reading
each arm's Parquet output. Reading every arm through one tool makes the
comparison about data, not file formats. All monetary arithmetic is
decimal arithmetic on the generated DECIMAL(15,2) columns, so sums are
exact and order-independent across engines; there are no floating-point
outputs to drift.

At SF0.1 and SF1 every run is checksummed in full. At SF10, runs 1 and 5
are checksummed in full and runs 2 to 4 are verified by row count plus an
ordered checksum of the first 100,000 rows (PREREG.md Section 7).
Row-count balance: no transformation in this study rejects or quarantines
rows, so rows out must equal the deterministic count from the inputs;
the checksum collector verifies row counts agree across arms for every
cell, and the runners log rows out for every run.

## Incremental protocol

Per scale: a full-refresh comparator build on base plus delta
(--full-refresh), then scenarios S1 (delta present from the start), S2
(delta arrives after staging), S3 (delta arrives after a completed run;
the fresh run merges it through unique_key), and S3b (late rows appended
to the input files themselves). T3 and T4 checksums must equal the
comparator in every scenario (H4). Incremental cost for H6 is the sum of
the T3 and T4 model times in S3's second run; full-refresh cost is the
same sum in the comparator build. Both come from run_results.json.

## Gate protocol

Faults are injected into copies of the SF0.1 inputs (src/inject.py).
For the clean input and each fault: staging models build, the gate tests
run, and the downstream models build only if every error-severity gate
test passes. Promotion blocked means caught, for F01 to F07 and F09.
F10 is warn severity by design: caught means flagged in the gate log
while promotion proceeds. F08 is scored by the incremental protocol: it
is caught when every scenario checksum equals the comparator, which is
the statement that the changed price was applied exactly once.
Gate evidence is results/gate_log.jsonl, with the failing test named for
every blocked fault.

## Hypothesis decision rules (operationalization)

The hypothesis texts are PREREG.md's. The numeric decision rules applied
to them, fixed in src/make_results.py before the SF1 and SF10 runs were
seen:

- H1: total workload ratio (sum of the six transformation means, DuckDB
  over Spark) at most 0.5 at both SF0.1 and SF1 means Supported; at one
  of the two, Partially supported; at neither, Refuted. Per-transformation
  ratios are reported beside the totals.
- H2: at SF10, any transformation ratio at least 1.5 means Supported;
  SF10 complete with no transformation at 1.5 means Refuted, reported as
  "no crossover observed inside the ladder tested"; SF10 not completed
  means Not yet measured.
- H3: every (scale, transformation) run-1 checksum equal across the three
  arms means Supported; any inequality means Refuted.
- H4: every scenario checksum equal to the full-refresh comparator at
  every scale means Supported; any inequality means Refuted.
- H5: catch rate at least 50 percent of F01 to F10 with zero missed
  critical faults means Supported; anything else means Refuted, with the
  numbers printed either way.
- H6: incremental saving above 50 percent at SF10 and at most 50 percent
  at SF0.1 and SF1 means Supported; saving above 50 percent at SF10 but
  also above 50 percent at a small scale means Partially supported;
  saving at most 50 percent at SF10 means Refuted.

## Threats to validity

- One machine, shared with other workloads during the build. The run
  log records the machine; a co-tenant load spike inflated early Spark
  attempts and is documented in DECISIONS.md (D4). Warm-up passes and
  five-run means are the mitigation in place, not a cure.
- Spark is local mode only. Nothing here measures a cluster, and the
  prose never claims it does.
- One dataset family, one set of six transformations, one dbt project
  shape. The crossover, if any, is a property of this workload on this
  machine.
- dbt model times and engine times have different bases (see Timing
  protocol) and are never ratioed against each other.
- The freshness gate (F10) checks shipdate recency against the generated
  data's own calendar (1992 to 1998). It tests the gate mechanism, not a
  production freshness policy.
