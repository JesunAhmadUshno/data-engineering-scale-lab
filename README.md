# Data Engineering at Scale Lab

Live dashboard: https://jesunahmadushno.github.io/data-engineering-scale-lab/

A pre-registered study on one machine (4 cores, 7.7 GiB RAM): DuckDB,
Apache Spark local mode and dbt on DuckDB run the same six frozen SQL
transformations over the same Parquet files, with checksums, a fault
matrix for dbt quality gates, and late-arriving data scenarios.
All data is derived from TPC-H with DuckDB's tpch extension and is not
comparable to official TPC results (see LICENSES.md).

## Question

RQ1: At what data scale, if any, does local Apache Spark beat a modern
single-node engine (DuckDB) on identical transformations, and what do
incremental dbt models with data-quality gates cost and catch compared
with full-refresh builds? Hypotheses H1 to H6 and their thresholds are in
PREREG.md; the numeric decision rules are in METHODS.md.

## Arms

- Arm A: DuckDB 2.0.0 over Parquet, canonical SQL in sql/.
- Arm B: Spark 4.0.1, local[*], same files and SQL.
- Arm C: dbt Core 1.12.6 with dbt-duckdb 1.11.1, same SQL with ref()
  wrappers (parity checked by src/check_sql_parity.py).

## Results (from RESULTS.md, generated by src/make_results.py)

Sum of the six transformation means, five measured runs per cell after
one warm-up pass:

| Scale | DuckDB total s | Spark total s | Ratio D/S | Bootstrap 95% interval |
| --- | --- | --- | --- | --- |
| SF0.1 | 1.48 | 11.86 | 0.125 | 0.115 to 0.136 |
| SF1 | 16.27 | 100.59 | 0.162 | 0.158 to 0.166 |
| SF10 | not tested | not tested | n/a | n/a |

| Hypothesis | Verdict |
| --- | --- |
| H1 speed at small scale | Supported (ratio at most 0.5 at SF0.1 and SF1) |
| H2 crossover at SF10 | Not yet measured (SF10 not run; this is not H2 being false) |
| H3 correctness | Supported (12 of 12 cells identical across all three arms) |
| H4 incremental correctness | Supported (every late-data scenario equals the full refresh) |
| H5 quality gates | Supported (10 of 10 faults caught, zero critical missed) |
| H6 incremental economics | Not yet measured; the SF1 saving of 70.5% already breaks the at-most-50% small-scale clause, so H6 can at best be Partially supported |

Under PREREG.md Section 2 the study passes only if every hypothesis
holds, so it is incomplete until SF10 is run. No second reviewer has
signed REVIEW.md yet. Checks run so far are listed in AUDIT.md.

## Reproduce

```
make check                 # SQL parity and the decision-rule checks, seconds, no data needed
python src/make_results.py # rebuild RESULTS.md, results/results.md, run_log.md, results/verdicts.json
make ci-check              # SF0.1 end to end, needs duckdb, pyspark and Java 21 (requirements.txt)
make reproduce SF=1        # generate data, run every arm, rebuild results
```

The dashboard builds with `cd site && npm ci && npm run build`; the build
first runs site/src/results.check.mjs, which recomputes the verdicts,
totals and intervals in JavaScript and fails if they differ from
results/verdicts.json.

## Limitations

- One machine, one dataset family, six transformations, Spark in local
  mode only. Nothing here measures a cluster or a cloud warehouse.
- SF10 was not run and SF30 was cut before pre-registration as a machine
  limit, so the crossover question is open.
- Five runs per timing cell, one run per late-data scenario and per
  setup measurement; intervals are bootstrap percentiles over n=5.
- Two sub-150 ms DuckDB cells exceed the 30% CV line (PREREG.md
  Deviation 2).
- dbt model times use a different timing base and are never ratioed
  against the engines.
